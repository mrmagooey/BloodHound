# AGENTS.md

## Architecture

BloodHound has two operating modes:

- **Standard mode**: Neo4j (graph) + PostgreSQL (application data), with authentication and UI
- **Standalone mode**: kglite (embedded Rust graph DB) + SQLite, no auth, single binary

kglite is a Rust-based embedded graph database that supports a subset of Cypher. It lives at `kglite-ffi/` as a git submodule and is linked into the Go binary via CGO as a static library (`libkglite.a`).

The DAWGS abstraction layer (`packages/go/kglite/dawgs/`) implements the same `graph.Database`, `graph.Transaction`, and `graph.Batch` interfaces as the Neo4j driver from `github.com/specterops/dawgs`. This lets analysis code run against either backend without changes.

Cypher queries generated by the Neo4j query builder pass through Go-side rewrites (`rewriteForKglite` in `transaction.go`) before reaching kglite's Rust parser/optimizer/executor. The rewrite layer handles three incompatibilities: label checks in WHERE clauses, pipe-separated relationship types, and parameterized IN lists.

## Build instructions

### Prerequisites
- Go 1.25.0+
- Rust stable toolchain (for building kglite)
- GCC / libc6-dev (CGO needs a C linker)
- Git submodules checked out: `git submodule update --init --recursive`

### Build kglite static library
```sh
cd kglite-ffi && cargo build --release --no-default-features --features ffi
```
This produces `kglite-ffi/target/release/libkglite.a`. **You must rebuild this after any changes to Rust source files.**

### Build standalone binary
```sh
CGO_ENABLED=1 go build -tags standalone -o bloodhound-standalone ./cmd/api/src/cmd/bhapi
```

### Build container
```sh
docker build -f dockerfiles/standalone.Dockerfile -t bloodhound-standalone .
```

## Testing

### Rust tests (kglite engine)
```sh
cd kglite-ffi && cargo test --no-default-features --features ffi
```

### Go e2e tests (kglite only, no Neo4j needed)
```sh
go test -v -tags e2e -timeout 30m ./cmd/api/src/test/e2e/
```

### Comparison tests (requires running Neo4j)
```sh
go test -v -tags 'e2e comparison' -timeout 30m ./cmd/api/src/test/e2e/
```
These run the same analysis against both kglite and Neo4j and compare results.

### AD_Miner regression tests
Located in the kglite Python test suite within `kglite-ffi/`.

## Common patterns

### Cypher rewriting (`transaction.go`)
The `rewriteForKglite` function in `packages/go/kglite/dawgs/transaction.go` applies regex-based transforms:
- `rewriteMultiTypeRel`: Converts `[:TypeA|TypeB]` to `WHERE type(r) IN [...]`
- `rewriteLabelWhere`: Converts `n:Kind` in WHERE to `hasLabel(n, 'Kind')`
- `rewriteInParam`: Expands `IN $param` to `IN [literal, ...]`

### Batch operations (`batch.go`)
`packages/go/kglite/dawgs/batch.go` buffers operations and flushes in bulk. Edge creation uses bulk FFI calls with deduplication (keyed on src/dst/type). Default flush sizes: 2000 (nodes), 5000 (edges).

### Profiler (`profiler.go`)
`packages/go/kglite/dawgs/profiler.go` provides `QueryProfiler` for per-query timing. Enable with `EnableProfiling()`, retrieve with `Report()`. Normalizes queries (strips IDs/params) for aggregation.

### CGO bridge (`kglite.go`)
`packages/go/kglite/kglite.go` wraps C FFI calls. Key types: `KnowledgeGraph` (main handle), exposed via `New()`, `Load()`, `Save()`, `Cypher()`, `CypherBatch()`.

## Known limitations

- kglite supports a Cypher subset, not full Neo4j Cypher. The Go rewrite layer bridges some gaps.
- Variable-length path patterns with multi-type relationships (`[r:Type1|Type2*]`) cannot be rewritten and must use single types.
- The Rust optimizer handles predicate pushdown for `type(r)` and `id(e)` expressions.
- MERGE with secondary labels has specific handling (see commit history).
- No APOC procedures - analysis code must use plain Cypher or Go-side logic.

## Golang code standards
- Receiver functions on structs should prefer `s` as the variable name instead of the first letter of the struct type.
- Named returns are not allowed; all return variables must be defined in the function.
- Group variable initializations in a `var ( ... )` block and hoist them to the top of the function when possible.
- Use `any` instead of `interface{}`.
- Prefer rich variable names, for example: `databaseInterface` instead of `di` or `dbi`.
- These standards apply to user/agent-written code, not auto-generated code (e.g., unit test mocks).

## Test code instructions for Golang
- If a test file tests internal (non-exported) logic, use the same package as the code being tested.
- If a test file only tests exported logic, use the package name with `_test` appended.
  - Example: `auth.go` has `package api`, `auth_test.go` testing exports should have `package api_test`
- Integration tests go in separate files (e.g., `auth_integration_test.go`) with a build tag: `//go:build integration` (or `serial_integration`, `slow_integration`).
